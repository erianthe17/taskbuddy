## Open questions

- **Client vs server email validation mismatch.** Client regex `^[^\s@]+@[^\s@]+\.[^\s@]+$` (LoginScreen.tsx:135) accepts `a@b.c`; backend `@IsEmail()` (auth.dto.ts:69-71) is stricter. A 400 returns `message` as a class-validator array and api.ts:789 shows `message[0]`, probably the raw "email must be an email" rather than friendly copy (1.1-09).
- **Login DTO has no length limits** (auth.dto.ts:69-76: email `@IsEmail`, password `@IsString @IsNotEmpty`, no `@MaxLength`), and the app sets no `maxLength` on either TextInput. Plan §4a asks that mobile limits match the DTO; here both are unbounded. Check what the server does with a huge body (1.1-13).
- **Case-sensitivity / trimming.** Email is trimmed only (AuthContext.tsx:410), never lowercased; relies on Supabase. Password is never trimmed (correct, but a pasted trailing space fails silently).
- **`handleSignIn` passes the untrimmed email to `onLogin`** (LoginScreen.tsx:163); trimming is done later in `signIn`. Fine today, but any other `onLogin` consumer would break.
- **Order in `signIn`** (AuthContext.tsx:409-416): `api.me` failing after a successful `api.login` shows the me-error and leaves no session persisted, while `adoptSession` (:265-271) persists first. A transient `/auth/me` failure on login therefore fails the sign-in with a possibly confusing message even though the credentials were valid (the 3-attempt retry used on restore is not used here).
- **Logout is fire-and-forget** (App.tsx:157 `void signOut()`; AuthContext.tsx:593,597 swallow errors). If `api.logout` fails the server-side token stays valid; and `signOut` clears state before the `await persistSession(null)` resolves, so a force-stop in that instant could leave the stored session (1.1-18 timing).
- **`signOut` depends on closed-over `session`** (AuthContext.tsx:583-599, deps `[persistSession, session]`); a stale callback could skip `api.logout` if `session` changed. Low risk.
- **`authError`/`signInError` persistence.** `shownError = error ?? signInError` (LoginScreen.tsx:130): a Google error held in context may show on the next Login visit, e.g. after logout, until `clearAuthError` runs (only called on Google tap, :174). Check whether a stale Google error appears after logout/switch.
- **Enter key does not submit** (`onSubmitEditing={Keyboard.dismiss}`, :97); product intent unknown.
- **Eye toggle and "Forgot Password?" lack testIDs/labels**; Maestro must use text or coordinates for "Forgot Password?", and the eye icon has no text at all.
- **Splash gate.** `minSplashDone || initializing` (App.tsx:459) holds the splash; if `/auth/me` is retried 3x at 1.5s (AuthContext.tsx:61-62,79-93) on a cold Render dyno, the splash can last ~30-60s with no error path. Time it in 1.1-19/20.
- **Hardware back with keyboard open** on Login: handler returns false (App.tsx:271), so the OS decides; confirm the exit only happens after the keyboard closes.
