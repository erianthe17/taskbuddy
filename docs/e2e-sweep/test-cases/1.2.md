### Code-reading observations (UNVERIFIED, suspected bugs / gaps)
1. Consent errors are never cleared after the box is ticked: `clearError` is not called for terms/privacy/dataCollection (RegisterScreen.tsx:505-508, 651-654, 671-674, 691), unlike name/email/password/category. Stale red text likely stays until the next submit (1.2-29).
2. `confirmPassword` error is not cleared when the user edits Password to match (clearError only touches its own key, Reg:566, 577) (1.2-19).
3. Double-tap guard is `if (submitting) return` on React state (Reg:351, 365), not a ref; two taps inside one frame could send two registrations, the second returning 409 and flashing "Email already in use" (Reg:379-383) (1.2-01).
4. Client regex `^[^\s@]+@[^\s@]+\.[^\s@]+$` (Reg:323) is looser than `@IsEmail()` (auth.dto.ts:16); the 400 reaches the banner as `message[0]` verbatim (api.ts:789, Reg:385) = the Register twin of E2E-009 (1.2-12/13/14).
5. No length cap anywhere on name, email or password: no `maxLength` on the inputs (Reg:137-151) and no `@MaxLength` on `full_name`/`email`/`password` in `RegisterDto` (auth.dto.ts:16-28). Consistent, but unbounded (1.2-41/42). Plan §4a mismatch rule has nothing to compare; flagged for product sign-off.
6. All-space password of length >= 8 passes the client check (Reg:331, no trim) and `@MinLength(8)` (auth.dto.ts:20) (1.2-22).
7. Name field inherits `autoCapitalize="none"` (Reg:145; FormInput has no prop to override), so names start lower-case (1.2-53).
8. Category list is hard-coded ids 1-5 (Reg:56-62); the fetch effect is an empty stub (Reg:306-309) and `setCategories` is never used. Correct only while DB ids match seed order (0004_seed.sql:5) (1.2-04).
9. Server does not enforce what the client does: `consented_terms/privacy/data_collection` are `@IsOptional` (auth.dto.ts:46-58) and a provider without `category_id` registers fine but gets no `provider_profiles` row (auth.service.ts:160). A direct API call bypasses the consent gate (backend gap; not exercised here because it would create an account).
10. Hardware back (and the back arrow) discards the whole form with no confirmation (App.tsx:267-269; Register unmounts) (1.2-46).
11. Duplicate-email UX shows the same fact twice: inline "This email is already registered." plus the "Email already in use" banner (Reg:381, 708-718) (1.2-38).
12. `signUp` fetches `api.me` BEFORE persisting the session (AuthContext.tsx:505-506): if `/auth/me` fails after a successful register, the account exists but the user sees an error and a retry then hits EMAIL_TAKEN (same ordering concern as Login's open question).
